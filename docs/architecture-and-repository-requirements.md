# AIAnimationSystem 架构优化与仓库重组需求文档

版本：v0.1 · 日期：2026-09-10 · 状态：需求梳理稿，尚未实施迁移

## 1. 需求概要

将仓库从围绕 MotionBricks 上游目录组织，调整为围绕 AIAnimationSystem 的数据处理、训练、模型、权重、推理、UE 插件和 UE 示例组织。MotionBricks 是其中一种模型实现，项目定位覆盖角色动画，不限定为 Locomotion。

在重组之前明确当前模型和数据链路；在重组之后保留现有能力与兼容契约，为后续改进动作表示、条件控制、生成质量和运行性能提供清晰边界。目录迁移与算法改造是两类独立工作，不应在一次无法归因的变更中混合完成。

本轮交付仅为需求文档。创建目录、移动代码或权重、修改模型、启动训练、创建示例项目和发布 Release 均不属于本轮执行范围。

## 2. 当前架构与事实边界

本章依据本次会话查看的源码描述结构，不是完整运行验收报告。仓库仍在变化，迁移执行前需要重新核对源码、工作区状态和可运行基线；不能把旧 README 的进度文字直接当作当前事实。

### 2.1 MotionBricks 参考模型

| 模块 | 当前结构 | 主要职责 |
| --- | --- | --- |
| Smart primitives / 控制逻辑 | 模型外的控制与约束构造 | 根据指令或事件生成目标关键帧 |
| Root | Transformer 与条件卷积解码器 | 预测片段长度及根节点轨迹 |
| Pose | Transformer Encoder 与多头 Token 输出 | 在轨迹和姿态约束下生成离散动作 Token |
| VQ-VAE | 时序卷积编码器、多头量化码本、条件解码器 | 训练时学习动作压缩与重建；生成时将 Token 解码为连续动作 |
| 参考预览 | 动作恢复、骨架/坐标映射、MuJoCo | 显示 G1 参考角色动作 |

参考推理主链路为“目标/历史姿态 → Root → Pose → VQ 解码 → 连续动作”。Root 条件与姿态关键帧也直接参与解码，并非仅通过 Token 间接传递。

G1 预训练权重与既定骨架、关节顺序、特征语义和码本绑定。改骨架、特征布局或码本，不代表仍可直接使用同一套权重；即使张量形状一致，也必须核对语义兼容性。

### 2.2 当前 UE 自定义数据路线

当前存在 UE 动画导出、自定义骨架、数据转换、VQ-VAE/Pose/Root 训练入口及质量相关工具。不同数据契约的允许行为不同：

- Schema v2 的 `pose_only_root_authoritative` 路线将身体姿态与独立 `root_frames` 分开。
- 该 pose-only 契约明确禁止训练 Root 模型；不能将上游 G1 的完整 Root → Pose 链路直接画成当前 UE 路线。
- 独立 Root 轨道用于恢复世界运动、审计和接触计算，不等于已经完成游戏移动系统到网络的条件接入。
- 预处理已有骨架/参考姿态/帧率/语义映射校验，以及动作家族划分入口和训练有效帧归一化统计。
- VQ-VAE 的 `native_quality` 分支已有有效帧掩码、几何、手脚端点、速度和接触相关损失；这些能力不能默认视为已经覆盖全部训练分支。
- Pose 训练冻结所用 VQ-VAE，检查数据契约并记录/校验对应权重哈希。
- 动画资产不能可靠提供的障碍物、落点和手部环境目标，当前明确标记为不可用。

### 2.3 已有推理工具与仍需验证的范围

当前已有 `export_unreal_inference.py`，用于导出 FP32 权重、骨架、统计量和配置，可选择 encoder-decoder 或 decoder-only。已有 `profile_unreal_inference.py`，测量单流神经网络推理，其说明明确排除 UE、上游 Token 生成器及动画后处理。

因此，不能继续笼统地说“推理包导出尚未实现”；也不能据此声称完整条件生成、UE 运行时、AnimGraph、移动系统接入和端到端性能均已验证。本轮未运行这些脚本、训练或 UE 示例。

## 3. 目标仓库结构

### 3.1 已确认的七个职责目录

```text
仓库/
├── data/                  数据处理链路
├── training/              训练、训练评估与训练配置
├── model/                 按模型名称隔离的模型源码
│   └── <modelname>/
│       └── 模型源码……
├── model-weight/          独立管理的模型权重
├── inference/             推理、推理包导出与部署验证
├── unreal-script/         UE 插件及 UE 专用脚本
└── unreal-sample/         UE 示例项目代码；Content 从 Release 下载
```

首个模型可使用 `model/motionbricks/`。这不要求立即实现第二种模型，也不要求提前建设通用模型注册平台。

七个目录是业务职责布局，不表示仓库只能包含这七个目录。README、许可证、构建/安装配置、文档、测试和自动化配置仍需有明确位置。辅助目录的最终布局属于实施设计，不在本轮强行定案。

### 3.2 每个目录的职责

| 目录 | 应负责 | 边界 |
| --- | --- | --- |
| `data/` | 数据清点、格式转换、清洗、校验、标注处理、骨架规范化、特征生成、数据划分、批次处理与人工验收工具 | 指数据处理链路，不默认意味着把所有原始数据提交到 Git |
| `training/` | 训练入口、训练配置、优化器/调度器、损失组合、采样策略、训练监控、质量评估、保存与续训 | 不持有推理必需的唯一一份网络或解码实现 |
| `model/<modelname>/` | 网络定义、编码器、量化器、解码器及该模型必需的表示/数学实现 | 不在导入时执行训练、下载权重、启动 UI 或加载 UE |
| `model-weight/` | 权重的标准定位、版本描述、下载说明及配套契约元数据 | 与源码分离；正式权重与临时检查点不能混为一谈 |
| `inference/` | 推理加载、输入条件整理、生成编排、输出恢复、推理包导出、精度一致性及性能测量 | 不依赖训练入口或训练评估脚本才能加载模型 |
| `unreal-script/` | 编辑器/运行时插件源码、UE 宿主内执行的脚本、UE 专用导出或自动化集成 | 不依赖示例项目专有 Blueprint、地图或 Content 路径 |
| `unreal-sample/` | 示例 C++、配置、项目描述、接入说明、Content 获取说明 | 示例资产从匹配的 Release 下载；不能将资产从别处夹带回源码仓库 |

### 3.3 容易混淆的归属

- 在 UE 编辑器中采样动画的脚本属于 `unreal-script/`；读取已导出文件并处理数据的 Python 脚本属于 `data/`。
- 训练质量评估属于 `training/`；导出前后数值一致性和部署延迟评估属于 `inference/`；数据入库前的校验属于 `data/`。
- 模型专用特征转换可随模型实现存放；通用数据校验/交换格式可由 `data/` 下轻量模块提供。训练与推理共用的变换必须只有一个权威实现。
- 模型相关的数学项可由模型模块提供，训练目标的组装和权重配置由 `training/` 负责。
- G1 中文预览界面属于推理演示的候选归属；现有启动器、EXE 和打包脚本需要单独清点，不能因为没有列入七个目录就直接删除。

## 4. 依赖与模块边界

以下为支撑目录重组的工程约束，具体 Python 包布局仍待设计。

### 4.1 依赖方向

```text
training ─────→ data 中的加载/契约模块
    └─────────→ model/<modelname>

inference ────→ model/<modelname>
    └─────────→ 轻量共享契约与数值变换（如确有需要）

unreal-sample → unreal-script 中的插件
unreal-script ↔ 导出数据 / 部署模型包 / 明确的运行时接口

model-weight = 被加载的产物，不是源码依赖层
```

依赖箭头表示代码依赖，和“数据经过哪个模块”的数据流不同。UE 插件无需为了离线训练而直接依赖整个 Python 工具链。

### 4.2 必须保留的边界

1. 纯模型导入不强制引入 Lightning、数据审核 Web 服务、MuJoCo 或 UE 工具；确属可选功能的依赖按使用场景安装。
2. 推理不能反向导入训练 CLI 或评估脚本以获得模型加载功能。当前导出脚本引用评估脚本加载函数的关系，是迁移时需拆分的具体边界。
3. 不把一个含混的旧 `helper/` 整体换个名字搬走；按真实用途归属，但不为了每个函数创建新层。
4. 不复制骨架、坐标转换、归一化和码本解释逻辑来消除依赖；应抽取最小共用实现。
5. 数据生产者、训练消费者和推理消费者使用一致的版本契约，对不兼容输入明确失败。
6. 插件是可复用功能提供者；示例项目是消费者，不反向成为插件的必要依赖。

### 4.3 路径不等于 Python 包名

`model-weight`、`unreal-script` 和 `unreal-sample` 是已确认的仓库目录名，不直接作为 Python import 名称。Python 可安装包、模块命名空间、CLI 名称以及是否暂时保留 `motionbricks` import 路径，需要实施设计确定。

不能依赖某个开发者的绝对路径、当前工作目录或临时 `sys.path` 拼接维持长期可用性。训练配置中的 Hydra `_target_`、检查点内保存的配置、脚本跨目录 import、启动器和安装配置必须一起审计。

## 5. 数据与权重需求

### 5.1 数据契约

建议保留并逐步明确以下字段类别；这不是要求本轮立即改写数据格式。

| 类别 | 需要表达的信息 |
| --- | --- |
| 骨架 | 标识、关节顺序、父子拓扑、参考姿态、语义骨骼映射 |
| 时间 | 帧率、时间戳、原始有效长度、填充帧掩码 |
| 空间 | 单位、坐标系、旋转表示、局部/全局空间定义 |
| 姿态与移动 | 身体姿态、独立 Root 轨道、Root/Pelvis 责任、运动契约 |
| 控制条件 | 条件类型、取值、坐标系、时间范围及可用性 |
| 来源 | 原资产、动作家族、处理版本、数据划分、质量状态 |
| 兼容性 | schema、特征版本、骨架/统计量签名、模型所需契约 |

独立 Root 位移与骨盆起伏必须区分。Pose-only 不意味着删除身体生成所需的运动信息，也不意味着把所有根节点相关特征清零。

缺失环境目标必须使用显式有效性表示。不能将零坐标当作“缺失”，也不能从动作名称臆造障碍物高度、落点或手部目标。

### 5.2 大数据与生成产物

原始动画、转换后的训练数据、缓存、日志、临时检查点和渲染报告，应分别明确保存位置、版本控制策略及生命周期。它们不因为 `data/` 或 `training/` 的存在就自动成为 Git 跟踪内容。

迁移不得顺便清理训练数据、删除原始动画、重跑昂贵数据处理或覆盖运行结果。已有批次队列、审核记录、训练路径及正在运行的进程必须在迁移前识别。

### 5.3 模型权重与推理包

`model-weight/` 是确认的权重目录。建议按模型、版本、变体组织，并让每份可用权重关联模型结构配置、骨架、特征语义、归一化统计量、码本关系和文件哈希。

权重分发采用 Git LFS、Release 还是外部模型存储，尚未确定。示例 Content 使用 Release 的要求不自动延伸为所有权重必须使用 Release。

需要区分训练检查点和推理包：训练检查点包含续训状态；推理包包含实际推理所需的权重、配置与数据契约。网络源码始终属于 `model/`，导出逻辑属于 `inference/`。正式推理包的最终物理落点可在实施时确定，避免重复拷贝造成版本分叉。

源码、上游预训练权重和第三方动画资产分别保留适用的来源与许可说明。目录重组不能改写上游归属，也不构成第三方资产的新增分发授权。

## 6. UE 插件与示例分发

### 6.1 unreal-script

目录名按用户要求保留，内容不局限于脚本，可以包含完整的 UE C++ 插件。插件应保留 `.uplugin`、`Source/`、必要配置及安装说明。

目录迁移优先保持现有插件名、模块名、反射类型、Blueprint API 和资产挂载语义。外部文件夹移动不应无意变成反射/序列化契约重命名；确需变更时必须另列兼容方案。

插件资源、图标或必要插件 Content 的分发方式需要清点后决定。用户已明确的是示例项目 Content 外置，不能不加区分地把所有插件资源一并删除。

### 6.2 unreal-sample

“only code”解释为源码仓库保留示例 C++ 和构建/打开项目必需的文本元数据：`.uproject`、`Source/`、`Config/`、相关构建规则及说明。不是只保留 `.h/.cpp`，否则无法形成可复现的 UE 示例项目。

地图、骨架、动画、材质和 Blueprint 等 `.uasset/.umap` 属于 Content，即使 Blueprint 包含逻辑，也随匹配的 Content Release 分发，不混入 C++ 源码交付。

### 6.3 Content Release 要求

| 要求 | 验收方式 |
| --- | --- |
| 源码与资产版本对应 | Release 说明标出对应 tag/commit、示例版本和 UE 版本 |
| 下载后能准确还原目录 | 文档写明解压位置，避免出现 `Content/Content/` 等层级错误 |
| 可校验 | 提供资产清单、包版本和校验值 |
| 引用路径稳定 | 按说明恢复后，示例地图、Blueprint、骨架与动画引用可解析 |
| 缺失行为清楚 | 未下载 Content 时明确提示缺少资产，不宣称完整示例已可运行 |
| 更新不覆盖用户工作 | 下载/安装流程明确目标目录及冲突行为 |
| 源码不重复存资产 | 示例 Content 不被普通 Git 或 LFS 再跟踪一份 |

首次迁移若已有 Content 被跟踪，需要先确认文件清单、可恢复副本和分发包，再处理跟踪状态。用户本轮没有要求重写 Git 历史；历史仓库瘦身属于独立决策。

示例数量、名称、演示地图和玩法范围尚未指定。第一版不自动扩展为完整游戏或多人示例套件。

## 7. 架构优化需求与建议优先级

用户要求分析优化方向。以下为建议排序，不是已批准的算法实施清单，也不保证未经测量的性能或生成质量提升。

| 优先级 | 建议 | 当前基础 | 目标与判断方式 |
| --- | --- | --- | --- |
| P0 | 统一数据契约与有效帧处理 | 已有 schema、签名和部分训练掩码 | 各阶段一致识别有效帧，错误契约明确拒绝 |
| P0 | 固定独立质量评估 | 已有质量损失/评估脚本 | 动作家族留出，区分重建、生成与交互控制质量 |
| P0 | 完成职责拆分与兼容迁移 | 当前入口与模型/数据工具有交叉依赖 | 同一输入和同一权重下，迁移不改变模型行为 |
| P1 | 显式运动条件输入 | 有独立 Root 数据不等于条件接通 | 相同历史姿态下改变速度/朝向，生成结果可验证地响应 |
| P1 | 逐步接入交互环境条件 | 当前缺少可靠环境目标 | 获得真实障碍物/落点/接触目标后再训练条件控制 |
| P1 | 优先统一训练骨架 | 已支持读取自定义骨架 | 先固定一种表示并重定向；任意拓扑混训是额外研究范围 |
| P2 | 完整推理与 UE 接入验证 | 已有 FP32 导出和局部推理测量 | 对齐导出前后输出，测完整生成与 UE 姿态消费路径 |
| P2 | 按瓶颈压缩网络 | 宽度、深度、码本等可配置 | 固定质量门槛，比较时延、显存、内存及稳定性 |

### 7.1 建议的游戏动画职责

普通移动建议由 CMC/Mover 等游戏移动系统负责位移模拟和运动权威，动画模型消费运动状态与轨迹条件生成身体姿态。Root 模型是否用于其他离线或受约束动作路径，单独设计；不把上游 Root 模型从整个仓库直接删除。

保留 Pose + VQ 解码主体建立基线，优先验证数据正确性、Tokenizer 重建能力和条件响应。需要交互位移的翻越、攀爬等动作，应明确动作阶段、轨迹与接触约束，不能简单套用普通移动路径。

这是目标架构建议，不是对现有 CMC/Mover 接入或联机验证状态的确认。

### 7.2 模型改造与权重兼容

| 改动 | 兼容性预期 |
| --- | --- |
| 调整外部关键帧策略 | 不改接口时可能保留现有权重 |
| 调整损失函数或训练采样 | 网络结构不变时可保留初始化，但需训练和重新评估 |
| 新增条件编码 | 旧层可能复用，新增层需训练；还需真实条件数据 |
| 改骨架、特征空间、归一化语义 | 不能默认兼容旧权重，需转换或重训方案 |
| 改码本、头数、Token 时间倍率 | Tokenizer 与 Pose 需要配套兼容或重训 |
| 替换生成范式 | 新模型研究，不纳入目录重组的完成条件 |

网络尺寸、具体推理后端、目标帧率、角色数量、延迟预算和量化方案均未确认。不得先写入虚构的性能承诺。

## 8. 架构图与文档表达要求

架构说明必须便于阅读：主链路突出、模块职责简短、配色有稳定含义，避免一屏堆满源码路径与长段落。用户明确希望科技感、美观、易读的链路图，而非只有干燥文字框图。

需要覆盖三个视角：当前 MotionBricks 模型、当前 UE 数据/训练路线、建议的目标优化路线。当前与规划使用文字标签和实虚线等方式共同区分，不能只依赖颜色。

图应明确 Encoder 的训练用途、解码器的生成用途、Root 条件的旁路输入，以及 G1/UE 两条路线的差异。复杂细节可通过交互展开或配套说明呈现，窄屏仍需可读。

会话中已提供三个视图的交互图；它是解释材料，不是当前仓库代码。后续长期架构文档应有可维护图源和版本，且随源码状态更新。具体导出格式尚未指定，不要求把图做成独立网站。

### 11.2 后续优化验收
